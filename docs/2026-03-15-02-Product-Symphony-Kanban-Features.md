# 产品篇：Symphony Kanban 到底是什么，一个 AI 个人工作台应该长什么样
如果说上一篇洞察篇回答的是“为什么值得做”，那么这一篇我想回答的是另一件更实际的事：
**Symphony Kanban 到底是什么？它不只是一个想法，它应该长成什么样，解决什么问题，又凭什么成立？**
我现在对这个产品的判断越来越清楚：
它不是一个新的 coding agent，也不是一个把终端能力搬到网页上的壳。它更像一个面向个人场景的 **AI 工作台**——一个把任务、workspace、调度、执行状态、人工审查重新组织到一起的系统。
换句话说，它解决的不是“AI 能不能写代码”，而是：
**当 AI 已经会写代码时，人类怎么更好地组织和管理这些工作。**
## 它不是在替代 IDE，它是在补上“工作管理层”
今天大部分 AI coding 工具，解决的是“局部执行问题”。
比如：
- 你在 IDE 里问一个问题；
- 你让 agent 修改一个文件；
- 你让它帮你生成一段逻辑；
- 或者在终端里跑一轮较长的任务。
这些都很有用，但它们大多数停留在“执行助手”层。
而当任务真正开始变复杂、开始并行、开始跨文件、跨仓库、跨阶段推进时，问题就不再只是“agent 会不会写”，而是：
- 任务在哪里被接住？
- 谁来维护状态？
- workspace 是怎么组织的？
- 哪个任务正在执行？哪个任务卡住了？
- 哪个结果值得 review？
- 哪个修改应该继续推进，哪个应该被打回？
也就是说，当前这类工具里，往缺了一层非常关键的东西：
**工作管理层。**
Symphony Kanban 想补的，正是这一层。
它不试图抢 IDE 的位置，也不试图取代 agent runtime。它站在上面一层，把“任务组织、状态推进、workspace 管理、执行观察、人工审查”这些原本散落在多个工具里的动作，重新组合成一套统一的工作系统。
## 产品的核心定义：一个面向个人的 AI 工作台
我现在最愿意给 Symphony Kanban 下的定义是：
> **一个把任务驱动、工作流编排、workspace 执行和 review 协作统一起来的 AI 个人工作台。**
这里面有几个关键词，每个都很重要。
### 第一，它首先是任务驱动的
这个产品的入口，不应该是一个聊天窗口，而应该是一个任务系统。
每一个任务都应该有清晰的结构：
- 标题
- 描述
- 优先级
- 标签
- 状态
- 所属工作区
- 关联执行记录
因为只有任务成为系统中心，后续的很多事情才会自然成立：
- 任务可以进入看板；
- 任务可以被调度；
- 任务可以被 review；
- 任务可以被拆分、被暂停、被合并；
- 任务执行结果可以被回挂到任务本身。
如果入口仍然是“对 agent 说一句话”，那整个系统迟早还是会退回到一次性协作模式。
### 第二，它必须理解 workspace，而不是只理解 issue
我越来越确信，AI 工作台不能只管理 task list，它必须同时管理 **workspace**。
因为对于 coding tasks 来说，一个任务最终不是停留在“卡片被完成”的状态，而是会进入一个具体的执行空间：
- 某个仓库或多个仓库；
- 某个 branch / worktree；
- 某个 agent session；
- 某一组修改；
- 某次 diff review；
- 某次测试或 dev server 验证。
也就是说，**workspace 才是真正承接任务执行的容器。**
没有 workspace 的任务系统，最终只会变成更漂亮的待办清单；
没有任务语义的 workspace 系统，又会退回成另一个复杂文件浏览器。
Symphony Kanban 的核心价值之一，就是把这两者真正绑起来。
### 第三，它必须把 review 变成系统中心，而不是附属动作
现在很多 AI coding 体验的问题，不是执行太慢，而是 review 太弱。
要么你不知道 agent 到底改了什么，
要么你知道它改了什么，但不知道这次修改在整个任务状态里意味着什么。
所以在我心里，Symphony Kanban 不是一个“发任务出去就结束”的系统，而是一个把 review 明确拉到中心的产品。
它应该能回答：
- 当前有哪些任务已经进入 review？
- 哪些任务只改了少量代码，可以快速通过？
- 哪些任务虽然完成了，但 proof of work 不够，不能推进？
- 哪些任务虽然 agent 自称做完了，但从 diff 或日志看明显有问题？
换句话说，review 不应该只是一块 diff 面板，而应该是整个产品里的核心路径之一。
## 产品的核心特性，不应该是“功能堆叠”，而应该围绕一条主线展开
如果只列 feature list，很容易把产品写成一堆好像都重要、但其实没有主次的能力集合。
我现在更愿意用一条主线来理解 Symphony Kanban：
> **任务被创建 → 任务被分类与组织 → 任务被调度进入执行 → 执行状态被可视化 → 人类在关键节点 review 与介入 → 结果被验证并推进。**
围绕这条主线，我觉得产品当前最核心的特性可以收敛成下面几组。
### 1. Issue 管理不是附属功能，而是产品入口
Symphony Kanban 的看板必须先是一个可靠的 issue 系统。
它至少要支持：
- 创建 / 编辑 / 删除任务
- 状态流转
- 优先级管理
- Tag 分类
- 子任务与依赖关系
- 过滤与多视图切换
但它和普通 kanban 工具的区别在于：
这些 issue 不是为了给人手动推进，而是为了成为 **AI 执行流的输入对象**。
也就是说，issue 的意义不是记录，而是驱动。
### 2. Tag 与 workflow 不是装饰，而是编排接口
在普通任务工具里，tag 通常只是分类标签。
但在 Symphony Kanban 里，tag 不应该只承担筛选作用，它更像 workflow 的轻量入口。
比如：
- `frontend` 标签意味着调用某类上下文与某类执行模板；
- `blocked` 标签意味着进入人工介入路径；
- `ci` 标签意味着执行完成后必须返回测试与校验结果；
- `research` 标签意味着任务进入偏资料收集型流程，而不是直接编码。
这时 tag 和 workflow 的关系就不再是“好看一点的筛选器”，而变成“状态推进与执行路由的控制点”。
### 3. Workspace 管理是产品区别于普通看板的关键
这是我觉得这个产品最该做深的一层。
每个任务不只是对应一个状态栏，而是应该能够展开成一个 workspace：
- 绑定本地仓库路径或远程仓库；
- 维护执行上下文；
- 记录 agent session；
- 展示变更文件、diff、日志；
- 支持启动 dev server 或测试；
- 必要时支持人工接管。
一旦 workspace 这层做实了，这个产品就不再只是“AI 版 Jira”，而会变成真正可用的 AI 工作台。
### 4. 执行状态必须透明，而不是只给最终答案
我不希望 Symphony Kanban 变成一个“任务已提交，请等待结果”的黑盒系统。
一个真正有价值的工作台，必须能把执行过程足够透明地呈现出来，至少包括：
- 当前状态
- 最近日志
- 最近一次 agent 行动
- 当前 diff
- 阻塞点
- 可回放的执行记录
透明的意义，不是为了让人类重新盯全过程，而是为了在真正需要介入时，能迅速建立判断，而不是重新追上下文。
### 5. Proof of Work 必须成为推进条件，而不是附加信息
这是我从 Symphony 身上吸收最深的一点。
如果 AI 工作台没有一套明确的 proof of work 机制，它迟早会退化成“agent 说它完成了，所以我们姑且信一下”。
这在 demo 里可以工作，在真实工作流里不行。
所以在 Symphony Kanban 里，任务推进至少应该依赖某种形式的交付凭证：
- diff
- test / CI 结果
- review 状态
- 日志摘要
- walkthrough / work summary
换句话说，推进条件应该由系统感知到的证据驱动，而不是只靠一句自然语言声明。
## 我目前最认可的产品分层
写到这里，其实产品分层已经比较自然地浮出来了。
我目前最认可的结构是四层：
### 前端呈现层：US 看板
这是用户真正交互的主界面。
它的职责包括：
- Issue 管理
- Tag 分类
- 视图切换
- Workspace 管理
- 路由与仓库路径入口管理
这里的“路径”，在产品语境里我现在倾向于理解成两层：
- 一层是前端路由；
- 一层是 workspace 对应的本地或远程仓库路径。
这两者都应该留在前端和工作区管理这边，而不是泄漏到底层执行逻辑里。
### 数据与网关层：API 后端
这一层的任务不是替代编排，而是成为前端和底层执行系统之间的缓冲带。
它要做的事情包括：
- 数据落盘
- 标准 CRUD
- 状态同步
- 任务、workspace、日志、执行记录等资源聚合
这样一来，前端不需要直接理解 agent runtime，前端只需要和一个稳定的数据接口打交道。
### 编排与调度层：Symphony
这一层负责真正的 workflow 推进：
- 自动获取任务
- 根据规则调度执行
- 管理工作流状态
- 触发或接收执行结果
- 把任务推进到下一阶段
它解决的是“任务怎么跑起来”，而不是“结果怎么展示”。
### 执行层：Opencode Server
这一层要尽可能无状态。
它的职责不是管理业务逻辑，而是纯粹接收调度请求、执行 agent 动作、返回结果。
比如：
- 分析代码
- 生成实现
- 修复 issue
- 执行命令
- 返回日志 / diff / 状态
我很喜欢这种分层方式，因为它天然保证了一件事：
**看板、存储、调度、执行各司其职，不会互相污染。**
## 这个产品真正难的地方，不是功能设计，而是边界设计
写产品的时候，很容易兴奋地不断加功能。
但我现在越来越觉得，Symphony Kanban 真正难的不是 feature list，而是边界。
比如：
- 哪些动作必须由前端触发，哪些可以自动调度？
- 哪些状态可以自动推进，哪些必须人工确认？
- workspace 的上下文应该保存到什么粒度？
- review 应该只是看 diff，还是要结合 proof of work 做更高层判断？
- tag 到 workflow 的映射，应该开放到什么程度，才不会把系统变成一团难维护的配置？
这些问题没有一个是靠“再多加一个按钮”就能解决的。
它们真正考验的是：这个产品到底有没有把“AI 工作台”理解成一个系统，而不是一个界面。
## 我希望这个产品最终表达出的气质
如果非要说我对这个产品的理想气质是什么，我希望它不是“炫技型”的。
它不应该让人觉得：哇，这里能同时跑 20 个 agent，好酷。
我更希望它给人的感受是：
- 工作被组织得很清楚；
- 状态变化是可理解的；
- 介入点是明确的；
- review 是顺手的；
- AI 很强，但并不失控；
- 人不需要一直盯着系统，但在关键时刻能接得住。
如果一个 AI 工作台最后能做到这些，那它才真的有资格成为“个人生产环境”的一部分。
## 下一步我最想验证什么
写完产品篇第一稿之后，我接下来最想验证的，不是更多 feature，而是三件基础问题：
第一，**最小可行版本里，哪些能力一定要一起出现，产品才成立。**
第二，**workspace、review、proof of work 这三件事，怎样组合起来才不会太重。**
第三，**前端看板、API 后端、Symphony、Opencode Server 这四层的职责边界，到底该切在哪。**
只有把这几个问题打透，这个产品才会从“方向正确”真正走向“可以开始做”。
## 结语
如果说洞察篇解决的是“为什么要做”，那这篇产品篇想解决的是“它应该具体是什么”。
到目前为止，我对 Symphony Kanban 的判断已经越来越明确：
它不是一个花哨的 AI 面板，也不是一个单纯的 agent launcher。
它应该是一套真正帮助人类管理 AI 工作的系统。
而一个真正有价值的 AI 个人工作台，不会把重点放在“生成更多内容”上，而会放在：
- 更好地组织任务
- 更清楚地推进流程
- 更稳定地承接执行
- 更高质量地完成 review
- 更有依据地决定下一步
如果这几点做对了，Symphony Kanban 才有机会成为一个真正可用的产品，而不是另一个看上去很聪明、但落地时一地鸡毛的 demo。


## PRD 文档
#### 1. 执行摘要（Executive Summary）

**问题陈述（Problem Statement）**  
当前 AI coding 工具（Claude Code、Codex、Gemini CLI、OpenCode 等）已经足够“会写代码”，但缺少一层针对 **任务、工作流、工作区和审查** 的“工作管理层”。开发者很容易陷入以下状态：

- 同时开着多个 agent/终端，难以知道当前哪些任务在执行、哪些被阻塞；
- 任务状态散落在聊天记录、终端输出和脑子里，缺乏统一视图；
- 不知道何时需要介入、review 哪个 workspace、哪些修改可以合并。

**拟解决方案（Proposed Solution）**  
构建 **Symphony Kanban**：一个面向个人开发者的 **AI 个人工作台**，以「任务驱动 + 可视化 workflow + Workspace + Proof of Work」为核心：

- 任务通过看板统一管理（创建、分类、流转）；
- 标签映射 Symphony `WORKFLOW.md` 的语义，并可视化展示状态推进；
- Workspace 作为执行容器，承接代码修改、日志、diff、测试与 session；
- Proof of Work（日志、diff、测试、review 状态）驱动任务推进，而不是“agent 说完了就算完”。

**成功标准（Success Criteria）**

1. **任务状态正确表现**：

- 任务在任何时刻的状态（Todo/In Progress/Review/Done/Blocked）与实际执行情况一致；
- 不出现“任务已经跑完但 UI 仍显示待执行”或“UI 显示完成但没有任何 proof of work”的情况。

2. **任务流转可靠**：

- 任务可以从创建 → 执行 → Review → 完成清晰流转；
- Blocked、重试、回滚等状态有明确语义和操作路径。

3. **标签覆盖 Symphony Workflow 语义且可视化**：

- 标签系统可以表达 Symphony `WORKFLOW.md` 中的关键 workflow 语义（例如：active/triage/review/blocked 等）；
- 标签与状态流转在 UI 中有直观呈现，用户可以从看板上理解任务在哪个 workflow 段。

## 2. 用户体验与功能（UX & Functionality）

### 2.1 用户画像（User Personas）

- **个人开发者 / 单人创作者**
    
- 使用多种 AI coding 工具（Claude Code、Codex、Gemini CLI 等），在一个或多个本地/远程仓库上开发；
    
- 希望把 AI 当“并行小工”用，而不是单个对话窗口；
    
- **技术主导的个人项目 owner**
    
- 同时维护多个 side project / 个人产品；
    
- 希望有一套统一的任务/工作流视图，管理 AI 与自己在项目上的协同。
    

> 不包括：团队协作、多用户 SaaS、企业级 PM 工具。

### 2.2 用户故事（User Stories）

1. **任务管理与执行流转**

> 作为一个个人开发者，  
> 我希望能在一个看板里创建和管理所有开发任务，  
> 这样我可以把这些任务分配给不同 AI coding agents 并行执行，而不需要手动记住每个任务的状态。

2. **标签驱动 workflow 可视化**

> 作为一个使用 Symphony Kanban 的用户，  
> 我希望通过标签来定义任务所处的 workflow 阶段，  
> 并在看板上直观看到每个任务当前在哪一步，这样我能快速判断哪些任务需要我现在介入。

3. **Workspace 作为执行容器**

> 作为一个经常同时操作多个仓库的开发者，  
> 我希望每个任务在 Symphony Kanban 中都能关联一个或多个 workspace，  
> 这样我可以进入对应工作区查看日志、diff、测试结果，而不必在不同终端之间来回切换。

4. **Review 驱动任务推进**

> 作为一个代码 owner，  
> 我希望在 Review 视图中能看到某个任务相关的变更、日志和 proof of work，  
> 这样我能够基于证据判断是否接受这次变更，而不是盲信 agent 输出。

5. **Blocked 与重试路径清晰**

> 作为任务负责人，  
> 我希望当任务在执行中出现错误或不可恢复状态时，它能自动进入 Blocked 并提示原因，  
> 并且能在一个明确的界面中让我选择重跑、修改上下文或手动接管。

6. **优先级视图快速排序**

> 作为个人开发者，  
> 我希望能够用四象限优先级视图快速归类任务，  
> 这样我能在多任务并行时更快决定先做什么。

7. **全局 MCP 服务提供**

> 作为使用多个工具的用户，  
> 我希望提供 MCP 服务，让 agent 直接通过 MCP 对看板上的任务进行增删改查。


### 2.3 验收标准（Acceptance Criteria）

**任务管理**

- 可以创建/编辑/删除任务，并设置：标题、描述、优先级、标签、状态、所属 workspace。
- 任务创建使用统一弹窗入口，至少包含 Workspace、标题、优先级、标签、描述与定时触发开关。
- 看板视图中，任务状态列（例如：Backlog/Todo/In Progress/Review/Done/Blocked）与任务实际状态一致。
- 提供任务详情页，可维护子任务拆解、调度配置与进程配置等关键信息。
- 提供优先级视图（Eisenhower 四象限），用于按优先级策略组织任务。

**标签与 workflow**

- 标签配置支持至少：类型（如 `stage:*`、`type:*`）、状态类标签（如 `blocked`、`ci-required`）。
- 标签可以通过规则映射到 workflow 行为，例如：
- 带 `ci-required` 标签的任务，在标记为 Done 前必须有测试/CI 结果。
- 带 `blocked` 标签的任务不会被 Symphony 调度层自动重新执行，除非用户手动解除。

**Workspace**

- 每个任务可以关联 1 个或多个 workspace（如不同 repo / worktree）。
- 用户从任务详情可以进入对应 workspace，看到：
- 最近执行日志（tail）
- 变更文件列表
- diff 视图
- 执行命令（可选）
- 提供工作区管理视图（列表 + 添加入口），并提供工作区配置页（路径与全局上下文规则注入）。

**Review 流程**

- 任务进入 Review 状态时，界面必须至少提供：
- 变更概览（包含 diff）
- 核心日志摘要
- 测试/CI 结果摘要（若有）
- 用户可以在 Review 视图中做三类明确决策：
- 接受并推进（例如标记为 Done）
- 打回（例如退回 In Progress 或 Blocked，并附加原因）
- 要求追加 Proof of Work（例如要求补充测试或更多日志）

**Proof of Work**

- 每一次“完成尝试”必须记录至少一条 proof of work：包括变更内容（diff 或提交记录）和简短说明（例如 agent 总结或手写总结）。
- 没有 proof of work 的任务不得自动进入 Done 状态。

**全局设置**

- 提供 MCP 服务 JSON 配置入口（`mcp_config.json`），全局作用于所有工作区。

### 2.4 UX 界面清单（基于当前 UX 设计稿）

- 1. Kanban Board View（含用户旅程提示、状态列、视图切换与新建入口）
- 2. Web Session Run View（嵌入式会话监控区域）
- 3. Review View（Agent 总结 / Diff 概览 / 测试证据）
- 4. Blocked/Error Handling View（错误提示 + 上下文快照 + 恢复操作）
- 5. Issue Detail View（子任务、优先级、调度与进程配置）
- 6. Tag & Workflow View（标签管理、工作流定义、生命周期钩子）
- 7. Workspace Management View（工作区列表与添加）
- 8. Workspace Settings View（路径配置与全局上下文注入）
- 9. Priority View（Eisenhower 四象限）
- 10. Create Task Modal（新建任务弹窗）
- 11. Global Settings View（MCP 服务集成配置）

### 2.5 非目标（Non-Goals）

当前版本 **明确不做**：

- 不做新的 coding agent，实现完全依托现有 agents（Claude Code、Codex、Gemini CLI、Opencode 等）。
- 不替代 IDE，不提供完整编辑器功能（只提供必要的查看/入口，而非全功能 coding 界面）。
- 不做多人协作/团队版：单人使用为主，不涉及用户管理/权限体系。
- 不做 SaaS / 云端版本：优先本地或用户可控部署环境。
- 不做 CI/CD 深度集成：仅关注任务与 workspace 层面的 proof of work，而非构建整套 CI/CD 体系。

## 3. AI 系统需求（AI System Requirements）

### 3.1 工具与接口（Tool Requirements）

- **任务/看板存储接口**：
    
- CRUD API：用于创建/更新/删除/查询任务、标签、状态。
    
- 状态事件接口：记录任务状态变化（包括时间、操作者、触发原因）。
    
- **Workspace 管理接口**：
    
- workspace 元数据（路径、关联 repo、当前 branch 等）。
    
- 执行记录（日志、命令、结果）的读写。
    
- **执行层集成接口**（通过 Symphony / Opencode Server）：
    
- 接收 Symphony 的任务 dispatch 请求；
    
- 收集执行结果（包括日志和变更信息）；
    
- 将结果回写任务和 workspace。
    

### 3.2 评估策略（Evaluation Strategy）

- **任务状态正确率**：
    
- 从日志/执行记录回放中抽样校验：实际执行状态与 UI 显示是否一致。
    
- **workflow 可视化完整度**：
    
- 检查标签配置 → workflow 行为 → UI 状态流转是否闭环；
    
- 不出现“标签已设置但不影响行为”的死配置。
    
- **proof of work 可追溯性**：
    
- 对每个 Done 任务，随机抽查：是否都能追溯到对应 workspace 的变更 / 日志 / 测试结果。

## 4. 技术规格（Technical Specifications）

### 4.1 架构总览（Architecture Overview）

采用四层架构：

1. **前端看板层（US Board）**

- 职责：任务视图、状态展示、标签/workflow 可视化、workspace 入口、review 流程 UI。
- 不负责：直接调度 agent，不直接读写底层日志文件。

2. **API 后端层**

- 职责：
- 数据落盘（任务、标签、workspace、执行记录、proof of work）；
- 提供标准 CRUD / 查询接口；
- 记录状态变化事件，作为状态机的“事实源”。
- 不负责：编排逻辑（不做 workflow 规则）、具体 agent 执行。

3. **Symphony 编排层**

- 职责：
- 定期拉取任务（例如依据标签/状态）；
- 根据 workflow 策略调度 agent 执行；
- 处理任务生命周期（claim → dispatch → resolve → land）。
- 不负责：前端渲染、物理执行命令（只调用执行层）。

4. **Opencode Server 执行层（或类似 runtime）**

- 职责：
- 真正执行 AI coding agent 的命令；
- 产生日志、修改代码、运行测试；
- 把执行结果回传给编排层/后端。
- 不负责：业务逻辑、任务抽象（只做“接单干活”）。

### 4.2 集成点（Integration Points）

- 看板 ↔ API：
    
- 任务/标签/workspace/执行记录的读写接口（REST/GraphQL）。
    
- API ↔ Symphony：
    
- Symphony 定期查询“可执行任务”；
    
- 将状态更新（In Progress/Review/Done/Blocked）回写后端。
    
- Symphony ↔ 执行层：
    
- 下发具体执行任务（代码修改、运行测试等）；
    
- 收集日志与变更信息，作为 proof of work 的原始数据。

## 5. 风险与路线图（Risks & Roadmap）

### 5.1 Phased Rollout（阶段规划）

**MVP**

- 任务看板（基础 CRUD + 状态列 + 标签）；
- 标签 → workflow 的简单映射（例如：标签控制是否进入执行队列）；
- 与执行层的最小集成（至少支持“记录执行开始/结束 + 回传日志链接”）；
- 最小版 Proof of Work：
- 记录每次执行的简单摘要 + diff 快照（或变更文件列表）。

**v1.1**

- Workspace 管理：
- 基础 workspace 列表 + 每任务关联 workspace；
- 查看最近执行日志、变更文件列表、基本 diff。
- Review 视图：
- 针对某个任务聚合日志/变更/测试结果，提供“通过/打回”操作。

**v2.0**

- 完整 Proof of Work 闭环：
- 为每次执行建立结构化记录（日志、变更、测试、评论）；
- 为 review/合并决策提供更强支撑。
- 更灵活的标签/workflow 规则配置（在保证可维护前提下的扩展）。

### 5.2 主要技术风险（Technical Risks）

- **workflow 过重**：
    
- 如果标签/规则设计太复杂，用户会觉得使用成本过高，反而放弃使用。
    
- **可视化维护难度**：
    
- 标签 → workflow → UI 状态 的映射可能变得复杂，影响可维护性。
    
- **执行记录规模膨胀**：
    
- 大量日志与 diff 的存储和查询可能带来性能问题，需要提前设计归档/聚合策略。
