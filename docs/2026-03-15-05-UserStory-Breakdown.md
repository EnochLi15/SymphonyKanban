# 把 Symphony Kanban 拆成用户故事：从 PRD 到 UserStory 列表

> 阶段对应：需求拆解 / MVP 规划 / 实施排期输入

本文基于 PRD、SPEC、UX 设计稿和当前技术架构稿，将 Symphony Kanban 拆成可执行的用户故事集合。拆解原则不是“把页面列一遍”，而是围绕核心价值流展开：

`任务创建 -> 任务组织 -> 自动调度 -> 执行可观测 -> 人工审查 -> 完成推进`

同时，所有用户故事都会尽量映射到四层架构：

- 前端看板层（Vue3）
- API 后端层（Express + SQLite）
- Symphony 编排层（TypeScript / `fizzy-popper`）
- Opencode 执行层（`opencode-ai/sdk`）

---

## 1. 拆解目标

- 把 PRD 中的高层用户故事拆成可排期、可验收、可分层实施的故事卡片。
- 先保证 MVP 的主价值流闭环，再补充增强型能力。
- 每个故事尽量具备明确的用户价值、触发条件、验收标准和依赖关系。

---

## 2. 用户故事分层

### 2.1 Epic A：任务入口与基础管理

目标：让用户可以用任务而不是聊天作为系统入口。

#### US-A1 新建任务

作为一个个人开发者，我希望能够快速创建任务，并填写标题、描述、优先级、标签和工作区，这样任务才能成为 AI 执行流的输入对象。

- 用户价值：建立统一任务入口
- 触发入口：Kanban 页的“新建任务”弹窗
- 涉及层：
  - 前端：新建任务弹窗、表单校验
  - API：任务创建接口、字段持久化
  - 数据库：`issues`、`issue_tags`
- 验收标准：
  - 可以创建包含 `title`、`description`、`priority`、`workspace_id`、`tags` 的任务
  - 创建后任务默认进入 `Backlog` 或 `Todo`
  - 创建事件被记录到 `issue_events`

#### US-A2 编辑与删除任务

作为一个任务 owner，我希望能够修改任务内容或删除无效任务，这样任务池能保持准确与干净。

- 用户价值：保证任务数据持续可维护
- 涉及层：
  - 前端：任务详情页编辑、删除确认
  - API：任务更新/删除接口
  - 数据库：`issues`、`issue_events`
- 验收标准：
  - 支持编辑标题、描述、优先级、标签、工作区
  - 删除任务需要确认
  - 状态变化与字段变化均可追溯

#### US-A3 看板视图浏览任务

作为一个个人开发者，我希望在一个看板中看到所有任务按状态分列展示，这样我能快速理解当前工作全局。

- 用户价值：建立任务总览
- 涉及层：
  - 前端：Kanban 列表、卡片组件、筛选与排序
  - API：任务列表查询接口
- 验收标准：
  - 按 `Backlog / Todo / In Progress / Review / Done / Blocked` 展示
  - 卡片显示标题、优先级、标签、工作区和简要执行状态
  - 看板刷新后与数据库状态一致

#### US-A4 优先级视图切换

作为一个经常并行处理任务的开发者，我希望可以切换到优先级视图查看任务，这样我能更快决定下一步。

- 用户价值：辅助决策排序
- 涉及层：
  - 前端：Priority View
  - API：任务查询与分组
- 验收标准：
  - 支持按优先级分组展示任务
  - 任务卡片可跳转回详情或看板

---

### 2.2 Epic B：标签与工作流定义

目标：让标签从“分类器”升级为“流程路由器”。

#### US-B1 管理标签

作为一个 Symphony Kanban 用户，我希望创建和维护标签，这样我可以用统一语义组织任务。

- 用户价值：建立可复用的任务语义体系
- 涉及层：
  - 前端：标签管理界面
  - API：标签 CRUD
  - 数据库：`tags`
- 验收标准：
  - 支持创建、编辑、删除标签
  - 标签包含名称、类型、颜色等基础属性

#### US-B2 将标签绑定工作流策略

作为一个系统配置者，我希望标签能映射到 workflow 行为，这样任务一进入某类状态就能被正确调度。

- 用户价值：让系统具备自动化路由能力
- 涉及层：
  - 前端：Tag & Workflow 配置界面
  - API：workflow 配置接口
  - 数据库：`workflow_defs`
  - Symphony：读取配置并执行规则
- 验收标准：
  - 可定义标签和状态之间的行为映射
  - 至少支持 `blocked`、`ci-required`、`research`、`frontend` 这类行为示例
  - 配置变更后，新的调度决策可生效

#### US-B3 可视化查看工作流

作为一个使用者，我希望在界面上看到标签如何影响任务流转，这样我能理解任务当前卡在哪个阶段。

- 用户价值：增强流程可理解性
- 涉及层：
  - 前端：Workflow 可视化
  - API：workflow 查询接口
- 验收标准：
  - UI 中能看到状态节点、连接关系、生命周期钩子
  - 用户可从任务状态和标签理解其当前 workflow 所在阶段

---

### 2.3 Epic C：自动调度与执行编排

目标：让任务能从 Todo 自动流入执行，而不是靠人手动追着 agent 跑。

#### US-C1 Todo 任务自动进入调度队列

作为一个个人开发者，我希望 Todo 任务能自动被 Symphony 发现并调度，这样我不需要重复手动启动 agent。

- 用户价值：减少机械操作
- 涉及层：
  - API：提供可执行任务查询接口
  - Symphony：轮询 / 订阅任务、执行 claim
  - 数据库：`issues`、`issue_events`
- 验收标准：
  - `Todo` 任务可被 Symphony 拉取
  - 被拉取后任务状态更新为 `In Progress`
  - 状态变更和调度原因被记录

#### US-C2 并发与排队策略生效

作为任务 owner，我希望系统按优先级和并发限制安排执行顺序，这样高优先级任务能先被处理。

- 用户价值：系统资源分配可控
- 涉及层：
  - 前端：任务详情页调度参数
  - API：调度参数保存
  - Symphony：并发控制与排队策略
- 验收标准：
  - 支持配置最大并发数
  - 超过并发上限时任务进入等待
  - 优先级更高的任务优先被调度

#### US-C3 Symphony 调用 Opencode 执行任务

作为系统本身，我需要把已调度任务交给执行层完成，这样产品才能闭环产出实际代码结果。

- 用户价值：这是执行链路的核心闭环
- 涉及层：
  - Symphony：适配 `fizzy-popper`
  - 执行层：`opencode-ai/sdk`
  - API：执行记录写回
- 验收标准：
  - Symphony 可根据任务与 workspace 上下文构造执行请求
  - 执行成功或失败后有统一回写格式
  - 失败任务不会静默丢失

---

### 2.4 Epic D：执行可观测性与 Proof of Work

目标：让用户不是“等结果”，而是“看得见过程和证据”。

#### US-D1 查看实时执行状态

作为一个开发者，我希望在看板和会话页面看到任务当前运行状态，这样我知道系统是否真的在工作。

- 用户价值：减少黑盒感
- 涉及层：
  - 前端：卡片状态、运行态视图
  - API：执行状态查询
  - Symphony：状态同步
- 验收标准：
  - 看板卡片显示运行中状态
  - Web Session 页面显示任务当前阶段
  - 页面刷新后状态保持一致

#### US-D2 查看日志、Diff 和测试结果

作为一个代码 owner，我希望看到日志、diff 和测试结果，这样我能判断这次执行是否可信。

- 用户价值：建立 Proof of Work 基础
- 涉及层：
  - 前端：Web Session / Review 页面
  - API：artifact 聚合接口
  - 数据库：`executions`、`execution_artifacts`
- 验收标准：
  - 可查看日志摘要
  - 可查看变更文件列表和 diff
  - 如果有测试结果，需可见

#### US-D3 完成任务必须附带证据

作为系统使用者，我希望没有证据的任务不能直接进入 Done，这样系统不会被“agent 口头完成”污染。

- 用户价值：保证完成状态可信
- 涉及层：
  - 前端：Done 操作前校验提示
  - API：状态转换校验
  - 数据库：artifact 存在性检查
- 验收标准：
  - 缺少日志 / diff / 摘要时，不允许自动进入 Done
  - 对 `ci-required` 标签任务，还需要测试或 CI 证据

---

### 2.5 Epic E：Review 与人工介入

目标：把 review 变成推进的中心节点，而不是附属页面。

#### US-E1 在 Review 页面审查任务结果

作为一个代码 owner，我希望在一个聚合视图里查看摘要、diff 和测试结果，这样我能快速判断是否接受。

- 用户价值：提升审查效率
- 涉及层：
  - 前端：Review View
  - API：Review 数据聚合接口
- 验收标准：
  - 页面展示 Agent Summary、Diff 概览、测试证据
  - 审查信息与最新一次执行记录一致

#### US-E2 批准、打回或要求补充证据

作为一个代码 owner，我希望可以明确做出“通过 / 打回 / 追加证据”的决策，这样任务推进有清晰治理机制。

- 用户价值：把人工判断纳入系统流转
- 涉及层：
  - 前端：操作按钮与原因输入
  - API：状态变更接口
  - 数据库：`issue_events`
- 验收标准：
  - 支持从 Review 进入 Done
  - 支持打回到 In Progress 或 Blocked
  - 支持记录打回原因或补充要求

#### US-E3 手动接管任务

作为任务负责人，我希望在必要时手动接管任务，这样 agent 卡住时我仍能继续推进。

- 用户价值：避免执行链路彻底中断
- 涉及层：
  - 前端：Take Over 操作
  - API：接管事件记录
  - Workspace：展示本地路径与执行上下文
- 验收标准：
  - 用户能从 Blocked 或 Review 直接看到对应 workspace
  - 接管行为被系统记录

---

### 2.6 Epic F：Blocked 恢复路径

目标：让失败不是“结束”，而是进入明确的恢复流程。

#### US-F1 执行失败自动进入 Blocked

作为任务负责人，我希望任务失败时自动进入 Blocked 并展示原因，这样我能第一时间知道问题是什么。

- 用户价值：减少失败状态的不确定性
- 涉及层：
  - Symphony：失败状态回写
  - API：Blocked 状态与错误信息持久化
  - 前端：Blocked 列与错误视图
- 验收标准：
  - 执行异常会触发 `Blocked`
  - 错误摘要与上下文快照可被查看

#### US-F2 在 Blocked 页面重试或补充上下文

作为任务负责人，我希望可以对失败任务进行重试或补充上下文后再次执行，这样我不必重建整个任务。

- 用户价值：降低恢复成本
- 涉及层：
  - 前端：Blocked 恢复操作
  - API：重试与上下文更新接口
  - Symphony：重新入队
- 验收标准：
  - 支持 Retry
  - 支持补充上下文后 Retry
  - 重试后产生新的执行记录

---

### 2.7 Epic G：Workspace 管理

目标：让任务真正绑定执行容器，而不是只停留在卡片层。

#### US-G1 查看和添加工作区

作为一个使用多个项目的开发者，我希望看到所有工作区并添加新的工作区，这样任务可以准确落到对应代码上下文。

- 用户价值：让任务与代码空间建立连接
- 涉及层：
  - 前端：Workspace Management View
  - API：workspace CRUD
  - 数据库：`workspaces`
- 验收标准：
  - 可查看工作区列表
  - 可添加工作区名称与本地路径

#### US-G2 配置工作区上下文

作为一个项目 owner，我希望给工作区配置全局规则与上下文，这样每次执行任务时 agent 都能带着正确背景工作。

- 用户价值：提升执行一致性
- 涉及层：
  - 前端：Workspace Settings View
  - API：workspace 配置保存
  - 数据库：`workspaces.context`
- 验收标准：
  - 支持保存本地路径、项目说明、编码规范等上下文
  - Symphony 发起执行时可读取这些上下文

#### US-G3 任务关联工作区

作为一个执行任务的开发者，我希望任务能关联到工作区，这样任务、执行记录和最终结果都能定位到正确仓库。

- 用户价值：确保执行上下文正确
- 涉及层：
  - 前端：任务创建 / 详情页
  - API：任务与 workspace 关联
- 验收标准：
  - 创建和编辑任务时可选择工作区
  - 执行记录可追溯到工作区

---

### 2.8 Epic H：MCP 服务能力

目标：让 agent 不只被动执行任务，也能主动操作任务系统。

#### US-H1 对外提供任务 MCP 服务

作为一个使用 agent 的用户，我希望外部 agent 能通过 MCP 操作任务系统，这样任务流可以更自动化。

- 用户价值：拓展系统边界
- 涉及层：
  - API：MCP 服务端点
  - 前端：全局设置展示
  - 数据库：任务、标签、工作区读写
- 验收标准：
  - MCP 可执行任务查询、任务创建、任务更新
  - 操作结果与 Web UI 保持一致

## 3. MVP 用户故事集合

为保证产品“最小可成立”，建议 MVP 只包含下面故事：

- `US-A1` 新建任务
- `US-A3` 看板视图浏览任务
- `US-B1` 管理标签
- `US-B2` 标签绑定工作流策略
- `US-C1` Todo 自动调度
- `US-C2` 并发与排队策略
- `US-C3` Symphony 调用 Opencode 执行任务
- `US-D1` 查看实时执行状态
- `US-D2` 查看日志、Diff 和测试结果
- `US-D3` 完成任务必须附带证据
- `US-E1` Review 页面审查任务结果
- `US-E2` 批准、打回或要求补充证据
- `US-F1` 执行失败自动进入 Blocked
- `US-F2` Blocked 页面重试或补充上下文
- `US-G1` 查看和添加工作区
- `US-G2` 配置工作区上下文
- `US-G3` 任务关联工作区

MVP 之外可后置：

- `US-A4` 优先级视图
- `US-E3` 手动接管任务
- `US-H1` MCP 服务能力
- 更复杂的 workflow 可视化编辑能力

## 5. 拆解原则补充

- 任务状态必须以 API 后端和 SQLite 为事实源，不能以前端本地状态为准。
- Proof of Work 是状态推进门槛，不是展示型附加信息。
- Workspace 不是设置页附属信息，而是执行上下文容器。
- Review 不是“看一下 diff”，而是任务推进的关键治理节点。
- Blocked 不是失败终点，而是进入恢复流程的开始。
